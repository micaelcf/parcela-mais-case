CPF protection, end to end

How patient.cpf_hmac and patient.cpf_ciphertext work together, why each exists, and what an attacker gets in each failure. Source decision: Q16 in grill-decisions-2026-10-27-pre-approval-journey.md.

In one paragraph. The CPF is stored twice, and neither copy is readable. The HMAC (keyed, deterministic) lets the database answer "is this the same CPF?": unique index, upsert, backoffice search. It can't be reversed. The AES-256-GCM ciphertext (randomized, reversible with the key) lets the app recover the digits when it really needs them, which is only the authenticated backoffice detail. It can't be compared. The public journey never shows any CPF digits. The two secret keys live in the app's environment, never in the database. A leaked dump therefore has no usable CPF as long as the keys don't leak with it.

1 · The three jobs, and why one column can't do all of them

Each candidate storage scheme against the three things the system needs from the CPF.

Scheme Find / dedupe by CPF
unique index, upsert, search		 Recover the digits
backoffice detail		 A leaked dump stays useless
no CPF recoverable
Plaintext yes yes no, the dump is a CPF list
SHA-256(cpf) yes no no, brute-forced in seconds (§2)
bcrypt / argon2 with random salt no, same CPF → different hash, so no equality lookup no yes
AES-GCM only (random IV) no, same CPF → different ciphertext yes yes, while the key is safe
Deterministic encryption (fixed IV) yes yes partly; fixed-IV GCM is broken (nonce reuse), needs AES-SIV
HMAC-SHA256 (key A) + AES-256-GCM (key B) yes, via cpf_hmac yes, via cpf_ciphertext yes, while the keys are safe

Only the pair covers all three jobs, because each column is optimized for one property the other must not have. Equality requires determinism, and safe encryption requires randomness.

2 · Why a plain hash is not protection: the CPF space is tiny

A CPF has 11 digits, but the last two are check digits computed from the first nine. There are only 10⁹ possible CPFs.

All possible CPFs
1,000,000,000 candidates
Unsalted SHA-256 brute force
public GPU benchmarks run SHA-256 at tens of billions of hashes/s, so the whole space falls in about a second [B]
…if a mask like ***.456.789-** were public
1,000 candidates, falls in milliseconds even in a browser (live demo in §6), which is why the public journey shows no CPF digits
HMAC-SHA256 without the key
no shortcut: each guess needs the 256-bit secret key, and guessing the key means 2²⁵⁶ tries
Why this matters: "we hash the CPF" sounds safe and isn't. Anyone with the dump can enumerate the space and recompute every hash. The HMAC's secret key is what turns a public function into one only the app can evaluate.
The HMAC's real limit: it stops offline brute force only while key A stays secret. If PII_HMAC_KEY leaks together with a dump, the attacker runs the same 10⁹ enumeration with the right key and recovers every CPF in seconds. The key is the protection; the algorithm alone is not.

3 · Write path: submitting the signup form

From the form to the row. Steps ① to ⑥ all run in the backend; the browser only sends the form over HTTPS.

Why normalize first

529.982.247-25 and 52998224725 are the same person. HMAC is byte-exact, so without one canonical form the unique index lets duplicates through.

Why the cpf:v1: prefix

Domain separation. If the same key is ever used for another field (e.g. phone), equal digits must not produce equal HMACs across fields. v1 names the scheme for a future migration.

Why AAD = cpf_hmac

It binds the ciphertext to its own row. Someone with DB write access who swaps two patients' ciphertexts gets a decryption failure, not a silently wrong CPF.

5 · Threat model: what each failure actually leaks

What the attacker got What they can do Verdict
DB dump / backup / managed-provider leak (most common) See cpf_hmac and cpf_ciphertext. Without key A they can't test guesses against the HMAC; without key B they can't decrypt. CPF safe names, phones, birthdates and incomes are plaintext by Q16's choice
Key A only (HMAC key) Brute-force all 10⁹ CPFs against the dump's HMACs, so every CPF is recoverable offline. CPF exposed this is why key A is as secret as key B
Key B only (encryption key) + dump Decrypt every ciphertext directly. CPF exposed
App host compromised (env + live DB) Everything: the app must be able to decrypt, so its host holds the keys. out of scope app-level encryption doesn't defend against this
DB write access, no keys Swap ciphertexts between rows to misattribute a CPF. detected AAD = cpf_hmac makes decryption fail
Public consultation link forwarded (Q13) See the patient's first name, the requested amount and the offers. no CPF no digits, no mask, no decryption on this path
Where the protection comes from: keys separated from data. On the all-in-one VPS (Q2b), the DB volume and the env file sit on the same disk, so a full-disk or full-host compromise defeats it. It pays off once the dump and the keys can leak independently: backups shipped elsewhere, or DATABASE_URL moved to a managed provider.

7 · Keys, versions and rotation

Two independent 256-bit keys

PII_HMAC_KEY (A) and PII_ENCRYPTION_KEY (B), base64 in env, validated at boot by the env schema (wrong length = the process refuses to start). Separate keys so each primitive's key serves one purpose. Reusing one key across HMAC and AES gives up the clean security argument for both.

Rotating key B (encryption): cheap

cpf_key_version says which key decrypts each row. Add key v2, write new rows with v2, re-encrypt old rows in batches (decrypt v1 → encrypt v2), then retire v1. The HMAC column doesn't change, so lookups keep working the whole time.

Rotating key A (HMAC): expensive

Every cpf_hmac must be recomputed, which requires decrypting every CPF with key B first, and the unique index is in play during the switch. Rotate only on suspected compromise, never on a schedule.

Losing a key

Losing B = every CPF is unrecoverable (the HMAC still dedupes, but nobody can read the digits back). Losing A = no new row can match an old one. The keys need their own backup, stored apart from DB backups.

8 · Where it lives in the code (one place)

Per the user's rule ("business logic and important rules centralized in one module/service"), all of this sits in a single PII module. Callers never touch node:crypto directly:

Responsibility Owner
Normalize + check digits CPF value object / schema refinement (shared by form and API)
blindIndex(cpf), encrypt(cpf, aad), decrypt(row) PII service, the only importer of node:crypto for PII; decrypt is callable only from backoffice code paths
Upsert by cpf_hmac Patient repository (database code, no crypto logic)
Deciding who may see the full CPF Backoffice route guard (Q12) + response shaping (Q13)

Invariants the tests must hold

Invariant Test
Formatting never changes identity blindIndex("529.982.247-25") === blindIndex("52998224725")
Encryption is randomized Encrypting the same CPF twice yields different ciphertexts, and both decrypt to the same digits
Ciphertext is bound to its row Decrypting with another row's cpf_hmac as AAD throws
Tampering is detected Flipping one ciphertext byte throws (GCM tag)
No plaintext at rest After a submission, no column of patient/consultation contains the 11 digits
No CPF on the public API Public GET/SSE payloads contain no CPF digits, and the public read path never loads key B
Bad keys fail fast Boot with a 16-byte key → env validation error, process exits

Grades: the CPF space (10⁹) is A, it follows from the check-digit algorithm. GPU SHA-256 throughput is B, order of magnitude from public hashcat benchmarks.

# Ops: compose, image, proxy, scripts

Verified on this workstation (2026-10-27): podman 6.0.2 rootless on WSL; `podman compose` delegates to **docker-compose v5.1.3** (so `depends_on.condition: service_completed_successfully` and `--wait` are honoured); bun 1.4.4; node 25.9.0. | Service     | Notes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `postgres`  | publishes `${POSTGRES_PORT:-5432}:5432`; dev password default `parcela`                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `caddy-dev` | same image and `Caddyfile` as `caddy`, no profile; same ports, published on `127.0.0.1` only (off the LAN on every engine); `APP_DOMAIN=parcela.localhost`; `CADDY_UPSTREAM=${DEV_UPSTREAM_HOST:-host.containers.internal}:3000` (the host's `vp dev`; `extra_hosts: host.containers.internal:host-gateway` for Docker, accepted by Podman); `CADDY_TRUSTED_PROXIES=private_ranges` and `CADDY_STACK_HEADER=X-Parcela-Stack dev`; `./.local/caddy:/data` bind mount, so the CA survives `vp run prune` |

caddy-dev and the prod-parity `caddy` share `.local/caddy` (one CA, one trust prompt per machine). They never run at once: they publish the same ports, `vp run up --prod` removes caddy-dev (`--remove-orphans`), and `vp run up` fails on busy ports while the prod stack runs (`vp run down` first).

Fully qualified image names only (Podman short-name policy). `env_file: .env` for app/worker/migrate. Inside compose, `DATABASE_URL` is `${STACK_DATABASE_URL:-postgres://postgres:5432}` plus `PGUSER`/`PGPASSWORD`/`PGDATABASE` from `POSTGRES_USER`/`POSTGRES_PASSWORD`/`POSTGRES_DB`: node-postgres (so drizzle and pg-boss too) fills user, password and database missing from the URL from the libpq `PG*` variables, and a full `STACK_DATABASE_URL` (a managed Postgres, audit A6) wins over them. No compose default nests another `${…}` (podman-compose ≤ 1.5 mis-parses it, audit N1). `POSTGRES_PASSWORD` stays required even with `STACK_DATABASE_URL`, because the bundled `postgres` still starts and gates `migrate` (audit N5). `LENDER_BASE_URL=http://app:3000/api/simulator/lenders`. Label every built image `com.parcela.project=parcela-mais-case`. In the prod configuration only `caddy` publishes host ports; `scripts/ops/lib/compose-stack.test.ts` fails otherwise.

## `Caddyfile` (one file for both stacks, env only, no nested placeholders)

```caddy
{
	http_port {$HTTP_PORT:8080}
	https_port {$HTTPS_PORT:8443}
	skip_install_trust
	pki {
		ca local {
			name "parcela-mais-case dev"
		}
	}
	servers {
		trusted_proxies static {$CADDY_TRUSTED_PROXIES}
	}
}

{$APP_DOMAIN} {
	encode zstd gzip
	header {$CADDY_STACK_HEADER:-X-Parcela-Stack}
	reverse_proxy {$CADDY_UPSTREAM} {
		flush_interval -1
		header_up X-Forwarded-For {client_ip}
		header_up X-Real-IP {client_ip}
	}
}

http://*.localhost {
	redir https://{host}:{$HTTPS_PORT:8443}{uri} 308
}
```

- **Sites.** `*.localhost` (and IPs) get a certificate from Caddy's local CA, root subject `parcela-mais-case dev - <year> ECC Root` (intermediate `parcela-mais-case dev - ECC Intermediate`), stored under `/data/caddy/pki/authorities/local/`. A public `APP_DOMAIN` gets ACME and needs `HTTP_PORT=80`, `HTTPS_PORT=443`. A bare `:<HTTP_PORT>` serves plain HTTP (RFC O1); it must equal `HTTP_PORT`, the only port published for HTTP. Verified with `caddy adapt`/`caddy validate` in the image for all three.
- **Redirect.** Caddy's automatic HTTP→HTTPS redirect never names `https_port` (it assumes that port is published as 443: `https://parcela.localhost/…`, observed), so `*.localhost` gets the explicit `redir` (observed: `308 https://parcela.localhost:8443/…`). A public domain keeps the automatic one. Bare `localhost` stays unmatched, so a bare-port site still answers it.
- **Client IP (RF-506).** `header_up` without `+` **replaces** any client-supplied value with `{client_ip}`. The prod `caddy` sets no `CADDY_TRUSTED_PROXIES`, so nobody is trusted and `{client_ip}` is the TCP peer: forged `X-Forwarded-For` is ignored. caddy-dev trusts `private_ranges`, so the dev stack keeps the client's `X-Forwarded-For` exactly like direct `:3000` did (the E2E suite isolates each test's rate limits with it), and marks its responses `X-Parcela-Stack: dev`; `test/e2e/proxy.spec.ts` skips the forged-header test there. Prod never trusts it.
- `flush_interval -1` streams SSE unbuffered. `skip_install_trust`: the container never touches a trust store; the host's is handled by `scripts/ops/lib/local-ca.ts`.

## Local HTTPS (`vp run up`, `vp run up --prod`)

`https://parcela.localhost:8443`: browsers resolve `*.localhost` to loopback themselves. The ops scripts never use the OS resolver for it: their health checks connect to `https://localhost:<HTTPS_PORT>` with SNI and `Host` set to `parcela.localhost` and verify the chain against `.local/caddy/caddy/pki/authorities/local/root.crt` (Bun `fetch` `tls: { ca, serverName }`). Node and Bun never read the OS store: Playwright's config sets `NODE_EXTRA_CA_CERTS` to that root. `doctor` warns (doesn't fail) when this host's resolver doesn't map `parcela.localhost`, with the hosts-file line.

`vp dev` listens on exactly one address: the one caddy-dev's container reaches (`scripts/ops/lib/dev-binding.ts`, chosen per OS and engine), never every interface. `localhost:3000` is therefore not the dev app's address on Windows + Podman and Linux: open the Caddy URL. `up` points `LENDER_BASE_URL` (app and worker processes; the process env wins over Bun's `.env*` loading) at `http://<that address>:3000/api/simulator/lenders` unless `.env.local` sets a non-`localhost:3000` URL. The worker talks to the dev server directly rather than through Caddy: no TLS, CA or `*.localhost` resolution in the worker, and caddy-dev's trusted `X-Forwarded-For` stays out of lender calls.

- **Windows + Podman (WSL VM, NAT)**: `host.containers.internal` is the VM itself (`169.254.1.2`), not Windows; a loopback listener isn't reachable from the VM (probed: `127.0.0.1`/`::1` refused). `up` binds `vp dev --host <vEthernet (WSL…) IPv4>` and passes the same address to caddy-dev as `DEV_UPSTREAM_HOST`. That adapter is a host-only virtual switch between Windows and the VM. Verified 2026-10-28: `192.168.1.67:3000` (Wi-Fi), `100.85.80.43:3000` (Tailscale) and `localhost:3000` refuse; `netstat` shows only `192.168.160.1:3000` listening; `https://parcela.localhost:8443` answers. caddy-dev's 8080/8443 are published on `127.0.0.1` only and refuse on those addresses too.
- **Windows + Docker Desktop, macOS (Podman's gvproxy, Docker Desktop)**: the engine forwards `host.containers.internal` to the host's IPv4 loopback: `--host 127.0.0.1`. Unverified live.
- **Linux + Docker**: `host-gateway` is the `docker0` bridge address, host-only: `--host <docker0 IPv4>`. Unverified live.
- **Linux + rootless Podman**: pasta maps `host.containers.internal` to the host's own address on its default-route interface, never to its loopback (by design: Podman issue #28435; `--map-host-loopback` would need a pasta option per network, outside compose). `up` binds that address, which **is** on the LAN: a host firewall must close port 3000 to it. `doctor` shows the address as a `!` warning with that hint. Unverified live.

Elsewhere the dev server isn't reachable from the LAN, and caddy-dev publishes on loopback only. Dev Postgres (`compose.dev.yaml`) still publishes 5432 on every host address, which on Linux and macOS includes the LAN (on Windows + Podman, published ports stay on the host: probed). `doctor` prints the address (`dev server address`) and, while both run, caddy-dev's request to it.

## Ops scripts (`scripts/ops/*.ts`, Bun, local only, no SSH, no git fetch)

`lib/engine.ts` picks `podman` if found on PATH or at `%LOCALAPPDATA%\Programs\Podman\podman.exe`, else `docker`; `CONTAINER_ENGINE` overrides. Compose is invoked as `<engine> compose -f compose.yaml -p parcela-mais-case` for prod/deploy/prune, and with `-f compose.yaml -f compose.dev.yaml` for `vp run up`, `vp run down` and `doctor`. Build-cache pruning runs only on Podman (label-scoped); on Docker it is skipped and reported, because BuildKit's cache carries no project label (audit A7). The runner also allows `certutil` and `security`, which only touch the current user's trust stores.

**Before `up.ts` (added 2026-10-28, RF-714).** The `up` script is `bun install && bun scripts/ops/ensure-env.ts && bun scripts/ops/up.ts` (arguments such as `--prod` reach `up.ts`). `bun install` is a no-op (~0.6 s) when nothing changed. `ensure-env.ts` writes `.env.local` only when it's missing: `.env.example` with fresh `PII_HMAC_KEY`/`PII_ENCRYPTION_KEY` (base64, 32 bytes) and `BACKOFFICE_SESSION_SECRET` (base64url), never rewriting an existing file. It's a separate process because Bun reads `.env.local` once, at process start. `vp run doctor` adds `dependencies` (✗ when a declared package has no `node_modules` folder; doctor itself needs the packages to start, so this catches packages added since the last install) and `.env.local` (`!` when missing: `up` creates it, `--prod` reads `.env`).

`scripts/ops/migrate.ts`: drizzle `migrate(db, { migrationsFolder: "./drizzle" })`, then install/upgrade the pg-boss schema (`new PgBoss({ connectionString, migrate: true, supervise: false, schedule: false }).start()` then `.stop()`), then create queues and schedules from `queues.ts`. It's idempotent. App and worker start pg-boss with `migrate: false`.

## Logging (tslog, added 2026-10-28, RFC D35)

One logger for the whole project: `src/server/lib/log/logger.ts` wraps [tslog](https://tslog.js.org/) (`createLogger(name?)`, the process's `logger`), with the same call shape as before, `logger.info(event, fields)`.

- **Dev (`vp run up`)**: pretty lines, `HH:MM:SS.mmm LEVEL event { …fields }` with the level in its colour. Each child's lines carry its prefix in its own colour (`[app]` bright cyan, `[worker]` bright magenta, padded to one column), and `up` gives the children `TSLOG_NAME` and, when its own stdout is a terminal (and `NO_COLOR` is unset), `FORCE_COLOR=1`, since their output is piped through it. The ops scripts log through `scripts/ops/lib/script-log.ts` (a tslog logger named after the script; `✗` lines at ERROR, `!` at WARN, the rest INFO). `backoffice:hash-password` prints its env line with `console.log`: that's the command's output, not a log.
- **Prod stack (compose)**: `TSLOG_TYPE=json`, one line per event: `{ "event", "level" ("INFO"…), "ts", …fields, "_logMeta": { "name": app|worker|migrate, runtime, hostname, … } }`. `TSLOG_TYPE=pretty` in the shell overrides it for reading by hand.
- **PII**: callers pass ids, codes and measurements only (RF-811); the logger also masks a fixed list of PII field names (`cpf`, `fullName`, `phone`, `email`, `cep`, …) as `[***]` in every output.
- **Tests**: `TSLOG_TYPE=hidden` prints nothing; tests that assert on log lines attach a JSON transport (`logger.attachTransport({ format: "json", write })`) instead of spying on `console`.

## Worker process (`src/server/worker.main.ts`)

Boots env, `boss.start()`, then `work("lender.<code>", { batchSize: 1, localConcurrency: <=20 }, handler)` per lender, `work("consultation.finalize", …)`, `work("throttle.purge", …)`. On SIGTERM/SIGINT: `boss.stop({ graceful: true, timeout: 15000 })`, then close the pool. Verify the exact `work()` concurrency option name against `pg-boss@12.38.0` types in S-worker.
